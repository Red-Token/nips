NIP-XZ
======

Simple HTLC Exchange over Nostr
-------------------------------

`draft` `optional`

## Rationale

Alice holds one asset. She owes Clair, who wants another. Bob holds both
and will trade at a price.

The cryptography for doing this atomically is settled: lock both legs to
the same hash, and the secret that unlocks one unlocks the other. What
has never had a home is the **negotiation** — how Bob advertises a price,
how Alice takes it, and what each of them must check before parting with
anything.

This NIP defines that negotiation, in three messages.

It does not define the settlement. Both legs are ordinary Lightning
payments, and the secret travels over Lightning, not over Nostr. A relay
that disappears mid-trade costs the parties their ability to talk; it
costs them nothing else.

### The secret belongs to a third party

This is the design's whole advantage and it is worth stating first.

In a two-party swap, one of the traders knows the secret and therefore
chooses whether to complete after seeing both legs locked. They settle if
the price still suits them and walk away if it does not, with the
counterparty's funds locked until timeout either way. That is a free
option, and it is written by the party who did not generate the secret.

Here the secret is generated by **Clair, who is being paid**. She is not
a party to the trade and has no interest in the price. She settles
because settling is how she receives her money. Neither trader can stall
for advantage, because neither trader holds the secret.

> **Clair does not implement this NIP.** She issues an ordinary invoice
> and is paid. She need not know that Nostr, Alice, or another asset were
> involved. A protocol that requires every participant to adopt it needs
> a network before it is useful; this one needs only the maker.

## Terms

* **maker**: The party who publishes an offer and holds liquidity in both
  assets. Bob, above.
* **taker**: The party who accepts a published offer. Alice.
* **destination**: The party being paid, in the asset the taker does not
  hold. Clair. **The destination is not a participant in this protocol.**
* **destination invoice**: The ordinary Lightning invoice the destination
  issued, carrying payment hash `H`.
* **counter invoice**: The **hold invoice** the maker issues to the
  taker, carrying **the same `H`**.
* **secret**: The 32-byte preimage `S`, generated by the destination and
  known only to her until she settles. `H = SHA256(S)`.
* **asset**: A network, identified by its **chain identifier**. See
  below. Assets have no name on the wire.

## Assets and networks

**A node exists on exactly one network.** A Lightning node is built for a
single chain and cannot hold channels on two. A maker trading between two
assets therefore runs **two nodes**, one per network, with two node IDs
and no shared identity. Nothing in this protocol lets one node stand for
both, and an implementation MUST NOT assume the maker's two nodes are
related except by the maker saying so.

The taker deals with exactly one of them: the maker's node on the
**`buy`** side, which issues the counter invoice and which the taker's
channel terminates at. The `sell`-side node is the maker's own business —
the taker never contacts it and has no way to verify it exists. What the
taker verifies is the counter invoice; what the maker promises is
delivery.

### Identifying an asset

An asset is a **chain identifier** and nothing else:

```jsonc
["sell", "0014868a826ddd4e7017b9a41ccb6f82ec08e5d511ee"]
```

**There is no name on the wire, deliberately.** A name cannot be verified
and cannot be acted on, so carrying one only creates something that may
disagree with the identifier beside it. An implementation that recognises
an identifier already knows what to call it; one that does not must
reject the message, and a name would not change that.

> **A name would not even help where it seems to.** `btc` says nothing
> about the network. `btc-signet` says nothing about *which* signet, and
> there are many. By the time a name is specific enough to be useful it
> is the identifier, restated less reliably.

Display names are a local concern. A wallet shows "BTC signet" because
**it** recognises the identifier, from its own table. Rendering a name
supplied by a counterparty is worse than rendering none, because it
presents an unverified claim in the place a user looks for the truth.

An implementation MUST reject any message whose chain identifier it does
not recognise. It MUST NOT infer a network from an invoice's
human-readable prefix, and MUST NOT accept an identifier on the grounds
that it resembles a known one.

The chain identifier is:

| Network | Identifier |
|---|---|
| mainnet, testnet | the genesis block hash |
| **signet** | the **signet challenge**, as hex |
| regtest | the genesis block hash |

> **Why signet is the exception, and why this is not pedantry.** Signet's
> genesis block is a constant asserted in chain parameters — **every
> signet has the same genesis hash**, including two that share no
> history. What separates them is the challenge, from which the network
> magic is derived. An implementation identifying a signet by its genesis
> would consider all signets one network.
>
> BOLT11 prefixes are no better: every signet invoice begins `lnsb`
> regardless of which signet issued it. Genesis, prefix and name are all
> insufficient for the same reason — **they describe a kind of network
> rather than a network** — and the failure they produce is an invoice
> paid on the wrong chain, caught, if at all, by a human reading an
> amount.
>
> A signet challenge is a scriptPubKey in hex: a single-key signet is
> `0014` — `OP_0` and a 20-byte push — followed by the hash160 of the key
> permitted to sign blocks. A 2-of-2 begins `5121` and runs to `52ae`. The
> shape varies; what matters is that it differs between chains that a
> genesis hash cannot tell apart.

## Theory of Operation

Three messages, then two payments.

1. The **maker** publishes an **offer** (kind `30200`): the pair, the
   price, the available volume, and where to reach them. Public and
   standing.

2. The **destination** issues an ordinary invoice to the **taker**, by
   whatever means they already use. This is outside the protocol.

3. The **taker** sends an **accept** (kind `23204`): the destination
   invoice, and the amount they expect to pay at the offered price.

4. The **maker** replies with a **confirm** (kind `23204`) carrying a
   **counter invoice** — a hold invoice, for the taker's asset, at the
   agreed amount, locked to **the same `H` as the destination invoice**.

5. The **taker** pays the counter invoice. It holds: the maker cannot
   settle it without `S`.

6. The **maker** pays the destination invoice. The destination settles
   it, because that is how she gets paid, and `S` is revealed to the
   maker as the payment completes.

7. The **maker** settles the counter invoice with `S`.

The taker's funds can only move if the maker holds `S`, and `S` only
exists in the open once the destination has been paid. **The taker
therefore cannot pay without the destination being paid.** That is the
whole safety argument.

Both channels are expected to exist before any of this begins. Opening
one is an on-chain transaction taking minutes to an hour, and nothing in
a priced negotiation should wait on a confirmation.

## Events

| Kind | Name | Addressable | Encrypted |
|------|------|-------------|-----------|
| `30200` | Offer | Yes (`d` tag) | No |
| `23204` | Trade message | No | Yes (NIP-44) |

### Offer — kind `30200`

Public, and addressable so that a maker can revise or withdraw it by
publishing again under the same `d`.

```jsonc
{
  "kind": 30200,
  "pubkey": "<maker>",
  "tags": [
    ["d", "<offer id>"],
    ["sell", "<chain identifier of the network the maker delivers on>"],
    ["buy",  "<chain identifier of the network the maker is paid on>"],
    ["price", "2083333", "ppm"],      // buy-units per million sell-units
    ["volume", "500000000"],          // msat of `sell`, available now
    ["min", "1000"]                   // msat of `sell`, smallest trade
  ],
  "content": ""
}
```

* `sell` and `buy` are chain identifiers, from the **maker's** side. A
  maker selling BTC for XBT is equally a maker buying XBT with BTC; which
  one is `sell` is a matter of direction, and a complete market is offers
  in **both directions**, not two kinds of order.
* `price` is expressed in parts per million to avoid floating point. An
  implementation MUST perform the conversion in integer arithmetic.
* `volume` is what the maker can deliver **now**, and is bounded by their
  outbound liquidity in the `sell` asset. It **depletes as trades
  complete**, and a maker SHOULD republish as it does.
* Both `sell` and `buy` MUST carry a chain identifier. An offer without
  one is malformed and MUST be ignored.

**The offer names no node.** The counter invoice does — a BOLT11 invoice
carries its destination — and that is the binding statement. A node
advertised in an offer would be an unverified hint that a taker might
treat as authoritative, and the taker either already has a channel to the
maker or does not; naming it changes neither.

### An offer has no expiry

There is no expiry field, and offers do not lapse. A maker manages the
offer's life by republishing it:

| To | Do |
|---|---|
| change the price | republish with the new price |
| reflect a completed trade | **republish with the remaining volume** |
| stop trading | republish with no tags and empty content |

A maker SHOULD republish after each trade, since `volume` that has been
consumed is no longer deliverable and an offer advertising it will draw
accepts the maker must abort.

> **Why no expiry.** An expiry is a promise about a future the maker
> cannot bind — they may withdraw before it, and nothing compels them to
> honour the offer until it. It would add a field that means less than it
> appears to. Withdrawal is unambiguous and immediate, and a maker who
> wants out uses it.

A taker judges freshness from the event's `created_at` and from whether
the maker answers. A stale offer costs a round trip, which is the same
cost as any other abort.

**An offer with no tags and empty content is withdrawn**, as NIP-XX
revokes a grant. A taker MUST treat a withdrawn offer as absent.

> **Why withdrawal is an empty event rather than a deletion request.**
> Deletion is advisory and relays honour it unevenly. A replaceable event
> with nothing in it is unambiguous, and it arrives by the same path the
> offer did.

An offer is an **invitation, not a commitment**. The maker is bound by
nothing until they issue a counter invoice.

### Trade message — kind `23204`

Encrypted, and addressed to one party. Every message MUST carry exactly
one `p` tag, and an `a` tag naming the offer, so either side can
reconstruct the trade without holding session state.

```jsonc
{
  "kind": 23204,
  "pubkey": "<sender>",
  "tags": [
    ["p", "<recipient>"],
    ["a", "30200:<maker>:<offer id>"],
    ["e", "<id of the message this answers>"]   // on confirm and abort
  ],
  "content": "<NIP-44 encrypted payload>"
}
```

The decrypted content is a JSON object with a `type`:

| `type` | Sent by | Carries |
|--------|---------|---------|
| `accept` | taker | the destination invoice and the expected amount |
| `confirm` | maker | the counter invoice |
| `abort` | either | a reason |

#### `accept`

```jsonc
{
  "type": "accept",
  "sell_chain": "<chain identifier>",
  "buy_chain":  "<chain identifier>",
  "destination_invoice": "lnbc...",
  "sell_msat": 120000,      // what the destination is owed
  "buy_msat": 250000        // what the taker expects to pay
}
```

Both chain identifiers MUST be restated and MUST match the offer. The
taker is asserting which two networks it believes it is trading between,
and a maker that disagrees MUST abort rather than interpret.

The taker states **both** amounts. `sell_msat` MUST equal the amount in
the destination invoice, and `buy_msat` MUST be what the offer's price
yields for it.

> **Why the taker restates a number the maker could compute.** It makes a
> disagreement about the price impossible to carry forward silently. If
> the offer moved between publication and acceptance, or either side
> rounds differently, the mismatch surfaces here — in a message that
> costs nothing — rather than in an invoice for the wrong amount.

A maker MUST verify both amounts against the live offer and MUST abort on
any mismatch. A maker MUST NOT issue a counter invoice for an amount the
taker did not state.

#### `confirm`

```jsonc
{
  "type": "confirm",
  "buy_chain": "<chain identifier>",
  "counter_invoice": "lnsb...",
  "buy_msat": 250000,
  "payment_hash": "<H, hex>",
  "cltv_expiry": 144
}
```

`buy_chain` names the network the counter invoice is on, and MUST match
the offer. It is carried explicitly because **the invoice cannot be
trusted to say so** — a signet invoice's `lnsb` prefix is shared by every
signet, so the taker cannot tell from the invoice alone which chain it
would be paying on.

The counter invoice MUST be a **hold invoice**. A maker who issues an
ordinary invoice will have it settled on receipt, before they hold `S`,
and will have been paid for a delivery they have not made.

#### `abort`

```jsonc
{
  "type": "abort",
  "reason": "volume exhausted"
}
```

Either party MAY abort before paying. After the taker has paid, an abort
is meaningless — the outcome is decided by settlement and timeout, not by
messages — and a party that has paid MUST NOT rely on one being honoured.

## What the maker MUST verify before confirming

1. **The maker can complete the trade.** A maker MUST NOT issue a counter
   invoice for a trade it cannot deliver — the outbound liquidity in the
   `sell` asset must be available at the moment of confirming, not merely
   advertised.

   **Avoiding overspend is the maker's job**, and it is theirs because
   they are the only party who can do it. The taker cannot see the
   maker's channel balances, cannot know what other trades are in flight,
   and has no way to reason about capacity that is being consumed by
   someone else.

2. **Both amounts match the live offer.** `sell_msat` equals the amount
   in the destination invoice; `buy_msat` is what the offer's price
   yields for it. A maker MUST abort on any mismatch and MUST NOT issue a
   counter invoice for an amount the taker did not state.

3. **The offer is still live** — not withdrawn, and not revised since the
   taker read it.

4. **The chain identifiers match the offer**, and the destination invoice
   is on the `sell` network. A maker MUST NOT pay an invoice whose
   network it has not verified, and MUST NOT rely on the invoice's
   human-readable prefix to establish it.

### Volume is advertised, not reserved

`volume` in an offer states what the maker could deliver when they
published. It is **not a reservation**, and accepting an offer claims
nothing. Two takers may accept the same volume simultaneously; the maker
confirms whichever it can serve and aborts the other.

That is wasteful — the loser has done work for nothing — and it is still
correct, because the alternative is worse:

> **Reserving volume would hand the taker the option this design exists
> to remove.** If accepting held capacity, a taker could accept several
> offers across several makers, pay the one that moved in their favour,
> and let the rest lapse — having tied up other people's liquidity for
> free. The maker would be writing an option, unpriced, to anyone who
> sends a message.

Aborting a taker costs them a round trip. Reserving for them costs the
maker real capacity. The asymmetry is deliberate, and it is why a maker
commits at `confirm` and not before.

## What the taker MUST verify before paying

This section is the protocol. The message formats are how material moves;
these are the rules that make moving it safe.

1. **The counter invoice's payment hash equals the destination
   invoice's.** If it does not, the two legs are unrelated and paying the
   counter invoice buys nothing. This is the single check that makes the
   trade atomic, and it is the one an implementation must never skip.

2. **The counter invoice's amount equals the `buy_msat` the taker
   stated**, which equals the offer's price applied to the destination
   amount.

3. **The counter invoice is a hold invoice.** An invoice that settles on
   receipt gives the maker the taker's funds before `S` exists.

4. **The counter invoice is on the `buy` network**, verified against the
   chain identifier and not against the invoice prefix. A taker holding
   channels on only one network will find a wrong-chain invoice
   unpayable; a taker holding several could pay on the wrong one.

5. **The timelock rule below holds.**

## The timelock rule

**The taker's outgoing HTLC MUST outlive the maker's payment to the
destination, with margin.**

The maker pays the destination *after* being paid by the taker, and can
only claim the taker's funds once the destination has revealed `S`. If
the taker's HTLC expires in between, the maker has paid the destination
and cannot be reimbursed.

```
expiry(counter invoice HTLC)  >  expiry(destination invoice HTLC)  +  Δ
```

Δ covers routing and settlement latency on the destination's chain.

> **Note who this protects.** Unlike a two-party swap, where the rule
> protects the party without the secret, here it protects the **maker**.
> The taker is safe regardless: their funds cannot move unless the maker
> holds `S`, and the maker cannot hold `S` unless the destination was
> paid. A maker who gets this wrong loses money; a taker who gets it
> wrong loses nothing.

A maker MUST verify this before paying the destination invoice, and MUST
abandon the trade if it does not hold. The `cltv_expiry` field in
`confirm` exists so the taker knows what the maker will require.

## Failure modes

| Situation | Outcome |
|---|---|
| Maker never confirms | Nothing has moved. Taker aborts |
| Taker never pays | Nothing has moved. Maker aborts |
| Maker never pays the destination | Taker's HTLC expires and refunds. **No loss; liquidity locked until timeout** |
| Destination never settles | Both legs expire. Everyone refunded |
| Maker pays the destination but cannot claim | **Maker loses.** Prevented only by the timelock rule |
| Relay disappears mid-trade | Settlement is unaffected — it is on Lightning. The parties lose the ability to abort or renegotiate |

### The residual option

Between the taker paying and the maker paying the destination, the maker
may decline to proceed. The taker's funds are then locked until timeout.

This is smaller than the option in a two-party swap: the maker gains
nothing by declining, since they are not paid unless they deliver, and
the taker's cost is delay rather than expense — there is no on-chain
transaction in the trade path to have wasted.

Implementations SHOULD keep counter-invoice expiries short, and MAY
decline to trade with makers who repeatedly let accepted trades lapse.
This specification does not attempt to price or prevent the behaviour.

## Passive orders

**A taker cannot rest an order.** The taker must send the payment, so a
fill requires their participation; nobody can fill them while they are
offline.

This follows from custody rather than from any choice made here. A
traditional venue fills a resting limit order while its owner sleeps
precisely because it is holding their funds and can move them unasked.
Without custody, there is nothing to move.

Makers rest; takers must be present. An implementation MAY publish taker
interest by some other means, but such a publication is a request for a
quote, not an order, and MUST NOT be presented to a user as something
that will execute unattended.

## Encryption

`accept`, `confirm` and `abort` MUST be encrypted with
[NIP-44](44.md). NIP-04 MUST NOT be used.

Offers are public and unencrypted. There is no encrypted offer form: an
offer nobody can read is not an offer.

## Relationship to other NIPs

| | |
|---|---|
| [NIP-44](44.md) | Encryption for trade messages |
| [NIP-XX](XX.md) | Node control. A party MAY drive their own node over NNC; this NIP neither requires nor notices it |
| [NIP-47](47.md) | Wallet access. Likewise — a party MAY make and settle invoices over NWC |

NNC and NWC are how you instruct **your own** node. NIP-XZ is how you
talk to **the other party**. The events never mix: node control is
between a controller and its service, a trade is between two
counterparties.

## Example flow

```
  maker (Bob)              relay              taker (Alice)        destination (Clair)
      |                      |                      |                      |
      |-- 30200 offer ------>|                      |                      |
      |                      |<-- reads offer ------|                      |
      |                      |                      |<-- invoice(H) -------|
      |                      |<-- 23204 accept -----|                      |
      |<---------------------|   (destination invoice, both amounts)       |
      |  verify price, volume|                      |                      |
      |-- 23204 confirm ---->|                      |                      |
      |   (hold invoice, same H)  ---------------->|                      |
      |                      |   verify H matches, amount, hold, timelock  |
      |                      |                      |                      |
      |<=========== pays counter invoice — HELD ====|                      |
      |                      |                      |                      |
      |============ pays destination invoice ============================>|
      |<---------------------- S revealed on settlement -------------------|
      |                      |                      |                      |
      |=== settles counter invoice with S =========>|                      |
```

Nothing after `confirm` passes over the relay.

## Open questions

1. **Amounts are millisatoshis on both sides.** Unexamined for assets
   whose smallest unit is not a satoshi.

2. **Discovery.** An offer is only as findable as the relays it reaches.
   How a taker finds relays carrying offers is the whole of the
   market-making problem and is deliberately out of scope.
